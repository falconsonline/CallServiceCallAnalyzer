# HTML Sequence Diagram — Design & Field Reference

Generated by `generate_transaction_html()` in `extract-callservice-logs.py` when `--html` is passed.

Produces a self-contained HTML file (mermaid v10, dark/light toggle, snapshot copy) showing the full hop-by-hop signalling flow for an extracted call.

---

## Node Chain

Participants are **dynamic** — one per entity seen in logs — in left-to-right order:

```
Remote Entity  ──SS7/SCTP──  signode1  signode2  ──internal──  TCAP-01  TCAP-02  ──app msg──  Call-01  Call-02
 (SSP/HLR/VLR)              (SmartSTP instances)              (TcapServer instances)           (CallService instances)
```

Only participants that appear in the extracted logs are included. A minimal call may have just one signode, one TcapServer instance, and one CallService instance.

| Participant | How identified | Example label |
|---|---|---|
| Remote Entity | DetailedTrace field[29] (`SSP` / `HLR` / `VLR`) | `SSP (SPC:1-234-1 / 2713)` |
| SmartSTP (per signode) | One participant per `--signode NAME:IP` arg; auto-detected from PCAP if omitted | `signode1 (Physical: 3-100-1 / 24577 \| Alias: 3-100-2 / 24578)` |
| TcapServer (per instance) | Filename: `TcapServer-03-*.log` → `TCAP-03` | `TCAP-03` |
| CallService (per instance) | TcapServer log content: `instance:#Call-02#scsca2` → `Call-02` | `Call-02` |

### SPC in participant labels

SPC is shown **once in the participant label** — not repeated on every arrow.

- Remote SPC: `SSP (SPC:1-234-1 / 2713)` — zone-region-sp format and decimal side by side
- SmartSTP SPC split into **Physical** and **Alias** sets per signode:
  - **Physical SPC** — OPC when `ip.src in our_ips` (outbound frame); DPC when `ip.dst in our_ips` (inbound)
  - **Alias SPC** — DPC when outbound; OPC when inbound; omitted when same as Physical
  - Example: `signode2 (Physical: 3-100-1 / 24577 | Alias: 3-100-2 / 24578)`
- Source: `mtp3.opc` / `mtp3.dpc` from tshark (ANSI fallback: `mtp3.ansi_opc/dpc`; M3UA fallback: `m3ua.protocol_data_opc/dpc`)
- Per-message arrow routing: determined by `ip.src`/`ip.dst` lookup against `node_ip_map`; falls back to the first signode alphabetically.

## CLI Arguments

```bash
# Full invocation with signode
python3 extract-callservice-logs.py \
  -s "applogs/SummaryTrace*" \
  -d "applogs/DetailTrace*" \
  -m "applogs/callservice-*" \
  -i <FSMId> \
  -p "pcaps/stp*.pcap*" \
  -t "applogs/TcapServer-0*" \
  --signode "signode1:172.26.131.18,172.26.131.19" \
  --signode "signode2:172.26.133.18,172.26.133.19" \
  -n "TestCaseName" --html -v
```

### `--signode NAME:IP1,IP2` (repeatable, optional)

Maps signalling node name to its Sigtran IP addresses. Used to:
1. Determine PCAP frame direction (`ip.dst in our_ips` → inbound; `ip.src in our_ips` → outbound)
2. Label the SmartSTP participant
3. Auto-detect OPC/DPC for the SmartSTP participant label

When omitted, direction is auto-detected by cross-referencing DetailedTrace `direction` field with PCAP `ip.src`/`ip.dst`.

## Arrow Structure (per message)

Each signalling message is rendered as **three arrows** — one per hop:

```
Remote  ->>  SmartSTP  :  [HH:MM:SS.mmm] opName (proto comp tcapType)
SmartSTP ->>  TCAP-03   :  [HH:MM:SS.mmm] opName
TCAP-03  ->>  Call-02   :  [HH:MM:SS.mmm] opName (proto comp tcapType)
Note over Remote,Call02 :  <enrichment fields>
```

- Solid arrow (`->>`) = request / invoke
- Dashed arrow (`-->>`) = response / result

Arrow label format: `[timestamp] decodedOpName (PROTOCOL compType tcapMsgType)`

## Operation Name Decoding

Arrow labels use human-readable names resolved by `_op_name()`.

**Label priority:**
1. **`_ws.col.Info` (`col_info`)** — Wireshark's own dissected Info column, checked first. Always correct and human-readable (e.g. `invoke initialDP`, `returnResultLast sendParameters`, `invoke eventReportBCSM`). Used as-is when present.
2. **CAMEL opcode map** (`camel.opcode` → `CAMEL_OP_MAP`) — fallback when `col_info` is empty.
3. **MAP opcode map** (`gsm_old.opCode` or `tcap.opCode` → `MAP_OP_MAP`) — further fallback.
4. **`event_name`** from DetailedTrace, or `'Message'` — final fallback.

## PCAP Authority Rules

When PCAP data is available, PCAP is the single source of truth for message count, direction, and timestamp.

- **Message count = PCAP frame count.** Detail records (DetailedTrace) that cannot be matched to a PCAP frame via `_best_pcap_entry()` are silently discarded. This prevents ghost message groups from appearing in the diagram.
- **Direction = PCAP ip_src/ip_dst.** After `all_msgs` is fully assembled (detail records + orphan pcap records), a direction-correction pass runs over every record that has PCAP IP data: `ip.dst in our_ips → 'in'`, `ip.src in our_ips → 'out'`. This overrides direction values from DetailedTrace or TcapServer logs, which may be stale or mismatched.
- **Timestamp = PCAP `frame.time`.** When a detail record matches a PCAP frame, the PCAP timestamp replaces the DetailedTrace timestamp. `_ts_to_sec()` handles both tshark ISO format (`2026-04-28T01:49:05.288539000`) and TcapServer `HH:MM:SS.mmm` format for timestamp comparison during matching.

## Anomaly Detection

TcapServer blocks where the message never reached CallService are highlighted in **red** using a mermaid `rect rgba(255,80,80,0.15)` band.

### Detection logic

A TcapServer block is an anomaly when:
- `thread_type = 'network'` (received from network)
- `forwarded_to_app = False` (no "Sending to App" line in the block)
- No matching DetailedTrace `direction='in'` record for the same `dialog_id`

### Anomaly types

| Type | Condition | Arrows |
|---|---|---|
| **DROPPED** | `forwarded_to_app=False`, `sent_to_nw=False` | `Remote ->> SmartSTP: ⚠ DROPPED opName` then `SmartSTP ->> TCAP-03 ⚠: ⚠ DROPPED opName` — stops here |
| **DIRECT RESPONSE** | `forwarded_to_app=False`, `sent_to_nw=True` | Above plus `TCAP-03 -->> SmartSTP: ⚠ DIRECT RESPONSE` and `SmartSTP -->> Remote: ⚠ DIRECT RESPONSE` |

TcapServer (`TCAP-03 ⚠`) appears as a diagram participant **only when anomaly or orphaned PCAP records exist** — otherwise it is transparent.

## HTML Features

### Dark / Light mode toggle

Fixed button top-right. Switches page palette and re-renders all mermaid diagrams with matching theme (`dark` / `default`). Default is dark.

### Copy as snapshot

| Button | Action |
|---|---|
| **📷 Copy** (per diagram) | Copies that diagram as a 2× PNG to the system clipboard |
| **📷 Copy All** (top-right) | Stitches all diagrams vertically into one PNG and copies it |

PNG background matches the active theme. Button flashes **✅ Copied!** on success or **❌ Failed** on clipboard permission error.

### Anomaly highlight

`rect rgba(255,80,80,0.15)` bands wrap every anomaly message group — visible in both dark and light mode.

## Key Functions in `extract-callservice-logs.py`

| Function | Role |
|---|---|
| `parse_detail_trace_records()` | Parses DetailedTrace logs into structured dicts (primary timeline) |
| `_detect_our_ips()` | Infers our Sigtran IPs from DetailedTrace direction + PCAP ip fields; accepts `--signode` override |
| `_parse_signode_ips()` | Parses `--signode NAME:IP1,IP2` args into `{ip: name}` map |
| `_enrich_flow_records_from_pcap()` | Runs tshark on PCAP, extracts all 38 fields, stores as `pkt_rec['pcap']` dict |
| `generate_transaction_html()` | Orchestrates: PCAP direction fix → anomaly detection → merge → Union-Find grouping → mermaid render |
| `_detect_our_ips()` | Auto-detects our node's IP(s) from PCAP correlation with DetailedTrace direction |

### Helper functions inside `generate_transaction_html()`

| Function | Role |
|---|---|
| `_op_name(r)` | Returns `_ws.col.Info` as primary label; falls back to CAMEL_OP_MAP / MAP_OP_MAP integer decoding; final fallback: `event_name` or `'Message'` |
| `_build_arrow_label(r)` | Builds concise mermaid arrow label string |
| `_build_note(r)` | Builds rich `Note over` content with all enrichment fields |
| `_mermaid(tx_flows)` | Renders one mermaid `sequenceDiagram` block for a transaction |
| `_best_pcap_entry(did, ref_ts)` | Matches closest-timestamp PCAP frame to a detail record by dialog_id |
| `_ts_to_sec(ts)` | Normalises ISO (`2026-04-28T01:49:05.288...`) and `HH:MM:SS.mmm` formats to seconds-of-day for timestamp comparison |
